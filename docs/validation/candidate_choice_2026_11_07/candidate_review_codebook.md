# 自然候选池初审

初审对象是每个合成情境一次生成的六条候选回复。只检查候选池能否支持有意义的选择，不判断哪条最符合某个角色，也不读取目标人格、后续选择结果、候选自标签或程序分数。所有原始候选及失败保留。

## 单条候选

对每条候选记录 `semantic_usable` 和简短理由。下列条件同时满足时为 `true`：

- 是可以直接交付给当前用户的完整自然语言回复，基本可理解；不是解释性标签、候选说明或残缺协议。
- 与当前分享有关，符合已提供的事实；没有把未支持的具体事件、他人意图或心理状态当作已知事实。
- 尊重明确用户边界；不以温和语气包装被拒绝的提问或建议。
- 作为当前社交场景的一种回应基本适切，没有明显无关任务、居高临下的判断或施压。

不要求文笔出色，也不要求候选提供建议、追问或行动。普通社交评价、清楚的比喻和玩笑不按字面虚假事实处理。低主动性的简短回应可以完全可用。候选之间相似不使单条候选自动不可用。

## 整个候选池

另记录 `at_least_two_distinct_usable`：是否至少存在两条可用候选，在实际互动取舍上不同，而不只是同义改写或口癖不同。可以体现为主要关注对象不同，或者回应后留白、邀请继续、推进新角度等互动方向不同。

该字段不要求覆盖全部人格目标或预设数值，也不要求每一条都不同。记录能说明差异的一对候选 ID 及理由；没有可支持的一对时填空数组。若差异难以判断，保守记 `false` 并说明。

## 输出与用途

输出 JSON 数组，每个情境一次，候选 ID 使用输入原值：

```json
{
  "scene_id": "输入中的情境 ID",
  "candidates": [
    {"id": "输入中的候选 ID", "semantic_usable": true, "reason": "依据实际文本和用户边界的简短说明"}
  ],
  "at_least_two_distinct_usable": true,
  "distinct_pair": ["候选 ID 甲", "候选 ID 乙"],
  "reason": "说明候选池是否存在真实的互动取舍"
}
```

示例值只是结构说明，不预设任何情境的结果。初审结果用于预先规定的整阶段继续或停止决策，不能逐条删除差候选后声称自动系统原本就能筛除它们，也不能重新生成到通过为止。若分析使用人工筛选作为独立诊断条件，应单独标明，并计入人工劳动；不得与未筛选自动路径混为一谈。
