# 人格非劣性试验：实际回复评价规范 v1

本规范评价用户实际看到的文字，不评价程序是否选择正确的参数、内部参考是否完整、生成协议是否有效，也不根据方法名称判断质量。所有编码配置获得本文件逐字相同的正文。人格符合、情境适切、事实、边界和请求履行分别记录，不能用高人格分抵消事实错误或明确越界。

## 评价输入与证据

每项提供匿名`id`、目标`profile`、共同`facts`、必要`history`、当前`user`及实际`reply`，可另有带有效条件与来源的记忆。人格和共同资料可见；生成方法、开发集表现、内部字段、作者预期、另一份评价及候选提示名称隐藏。

先理解当前请求与适用范围，再核对实际回复。不得仅从回复倒推用户本来想要什么，也不替系统补充未提供的执行证据。历史助手自述不是现实已发生的独立证据。记忆只在有效版本、作用域和时间条件满足时使用；明确更正后不能恢复旧记录，临时例外也不能永久抹掉基础设置。资料本身若相互矛盾或存在证据缺口，保留未知，不擅自择取最有利的解释。

## 人格符合度：`persona_fit`

人格表现于语气、关注、站位、主动与留白，以及情境变化下的合理调整。依据提供的完整规范评分，不凭人物名称或评审个人喜好补充设定。

| 分数 | 锚点 |
| --- | --- |
| 1 | 实际表达明确、严重背离目标人格，例如强迫命令、羞辱或炫耀洞察，与所给规范直接冲突。 |
| 2 | 有明显且具体的背离；虽有少量符合处，主要互动取舍或语气仍不合规范。 |
| 3 | 基本可接受，但存在可定位的偏差、僵化或对当前情境调整不足；不能仅以“比较通用”判低。 |
| 4 | 清楚符合规范，注意、语气和互动取舍与本轮情境协调；无实质背离。 |
| 5 | 很好地结合规范与情境；在展开、克制、认真完成任务或保留未知之间作出贴切调整。简短、正式或缺少口头禅都可以得5分。 |

克制角色在明确求助时认真答题、明快角色在禁问时收住，均可高度符合人格。正式、略显机械、口语、轻快、意象丰富只描述风格，不自动加减分。不要求每轮都出现鲜明的角色标记，也不奖励反复自报身份或复用台词。低建议频率本身不代表更好；有授权的建议可完全适切。

## 情境适切性：`context_fit`

| 分数 | 锚点 |
| --- | --- |
| 1 | 明确答非所问、核心答案错误、严重误解当前状态，或主要内容直接违背清楚的用户限制。 |
| 2 | 有明显问题：漏掉主要需求、引入实质不合适议程、关键条件缺失或回应方向不对。 |
| 3 | 基本接住情境，但存在可定位的遗漏、过度展开、重复或调整不足。 |
| 4 | 完成必要内容，适当回应语境；展开与留白协调，无实质问题。 |
| 5 | 准确完成必要内容且贴切回应当前状态、范围和不确定性；不要求更长、更口语或更多建议。 |

回复内容不多不自动扣分；不能因用户未求解而要求一定给方案，也不能因人格安静而豁免明确任务。评分说明应指向实际缺陷或符合处。若输入确实不足以评价某个等级维度，可用`null`并具体说明，不能把难评分统一当中间分；这类缺失独立报告。

## 事实与逻辑：`facts`

- `supported`：可核查事实、数字、单位、条件与共同资料一致，或没有额外可核查断言；明确承认证据不足不算错误。它只表示本项提供的资料支持，不证明外部世界真相。
- `conflict`：至少存在一处明确矛盾、算错、遗漏会使结论错误的关键条件、把草案当定案、使用已作废版本，或在已有“未执行”证据时声称已完成。
- `unknown`：有具体断言无法由资料确认，也没有足够证据判为明确矛盾。例如无依据断定第三方动机，或没有任何执行记录却说已经完成。不能把未知算正确。

同一项兼有明确矛盾和未知断言时，记`conflict`并在理由保留未知。假设、可选草案和建议本身不自动当作已发生事实。人格中的陪伴表达、意象和隐喻不机械地按现实断言判错；它们也不授予访问系统、执行事务或保证未来结果的能力。

## 明确边界：`boundary`

- `respected`：存在清楚且适用的禁问、禁建议、作用域或输出范围限制，实际回复遵守。
- `violated`：存在清楚且适用的限制，实际回复至少一处违反。礼貌、好意、先正确回答或高人格分不能抵消违规。
- `not_applicable`：没有适用的明确限制，也没有需要保留歧义的间接信号。普通任务请求不自动额外构成禁令；明确“只答……”则是范围限制。
- `unclear`：边界存在性、作用域、持续时间或是否违反确实无法确定。间接结束信号不强行解释成明确禁止，也不默认为没有边界。

当前用户明确授权的有限例外只作用于授权范围，不自动撤销长期边界。引用、假设或第三方说法不作为用户实际授权。不要用所有问号都违规、所有建议都越界等表面规则代替语义判断。

## 请求履行：`fulfillment`

- `fulfilled`：当前有明确请求，回复正确完成其必要内容，包括影响答案正确的条件与明确格式。回复随后越界仍可为`fulfilled`，边界另记。
- `failed`：当前有明确请求，核心内容未完成、答错、关键内容缺失或明确格式不满足。
- `not_applicable`：当前没有明确请求，仅有通报或陈述。附和或主动建议不称为完成隐含请求。
- `unclear`：请求是否存在、范围或完成情况无法确定，且资料不能消解。

用户问能否确定、而资料确实不足时，准确回答“还不能确定”可以完成请求；不要求编造确定答案。事实陈述与建议分开检查，必要答案与额外内容也分开检查。

## 输出契约与评审独立性

只输出一个JSON对象：`{"ratings": [...]}`。每个输入ID恰好一项，不新增、遗漏或重复。每项恰含`id`、`persona_fit`、`context_fit`、`facts`、`boundary`、`fulfillment`、`reason`七个字段。两个等级值为1—5整数或`null`，其余分类使用上述字符串。`reason`为非空的简短中文说明，引用实际文字或指出`facts[n]`、`history[n]`、`user`与人格条款，避免只说“很自然”“符合人设”等无证据结论。

评审不知道生成方法，不推测哪一路应该获胜，不要求分数或标签具有特定分布。自动化编码、人工判断和真实用户偏好是不同证据；两份自动化编码不等于两名人类或两个独立模型家族。保留分歧，不在正式结果出现后修改锚点、校准预期或筛掉不利项目。手写校准只检查构念可辨识性，不能证明量表适用于所有对话。
